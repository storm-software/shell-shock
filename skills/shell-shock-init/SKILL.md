# Shell Shock project setup

Shell Shock is a file-routed CLI framework: every `src/<name>/command.ts` becomes the `<name>` command of the generated binary. Building is done by Powerlines through `@shell-shock/core/api` — there is no `shell-shock` CLI binary, so the project needs a tiny `build.mjs` (below).

## 1. Resolve the target

- Use the directory the user named; ask only if they gave none. Create it if missing.
- If it already has a `package.json`, `shell-shock.config.ts`, or `src/run/command.ts`, **merge** — never overwrite existing files without asking. Add only missing keys to `package.json`.
- CLI name: user-supplied, else the kebab-cased directory name. Used for `name` in config and the `bin` key.
- Package manager: the lockfile in the target dir or nearest ancestor (`pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `bun.lock*` → bun, `package-lock.json` → npm). None → pnpm if installed, else npm.
- **Inside a pnpm workspace that contains the `@shell-shock/*` packages** (e.g. this repo's `playground/`): use `"workspace:*"` versions instead of installing from npm, and copy the neighbouring playground's `tsconfig.json`/`project.json` shape rather than the standalone tsconfig below.

## 2. Install dependencies

```bash
<pm> add @shell-shock/core @shell-shock/preset-cli zod
<pm> add -D typescript @types/node
```

`preset-cli` brings banner, help, console, completions, prompts, theme and update plugins. If the user wants a lean single-purpose script, swap it for `@shell-shock/preset-script` (and import `plugin as script` from it in the config).

## 3. Files to write

### package.json (merge)

```json
{
  "type": "module",
  "bin": { "<cli-name>": "./dist/bin.mjs" },
  "scripts": {
    "build": "node build.mjs",
    "start": "node dist/bin.mjs"
  }
}
```

`"type": "module"` is required — generated output is ESM. The build may add an `exports` map itself; leave that to it.

### shell-shock.config.ts

```ts
import type { UserConfig } from "@shell-shock/core";
import { defineConfig } from "@shell-shock/core/config";
import { plugin as cli } from "@shell-shock/preset-cli";

const config: UserConfig = defineConfig({
  name: "<cli-name>",
  output: {
    storage: "fs"
  },
  plugins: [
    cli({
      theme: {
        labels: {
          banner: {
            header: "<Cli Title>"
          }
        }
      }
    })
  ]
});

export default config;
```

Commands are read from `src/` by default; set `input: "src/commands"` only if the user wants a different folder (and put commands there instead).

### build.mjs

```js
import api from "@shell-shock/core/api";

const command = process.argv[2] ?? "build"; // build | prepare | clean | docs | lint

await api({
  command,
  options: {
    cwd: process.cwd(),
    root: ".",
    configFile: "shell-shock.config.ts",
    framework: { name: "shell-shock", orgId: "storm-software" }
  },
  inlineConfig: { command, root: "." }
});
```

This mirrors what `@shell-shock/nx`'s executors pass to the same API.

### tsconfig.json

```json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true,
    "types": ["node"]
  },
  "include": ["src/**/*.ts", "shell-shock.config.ts", "shell-shock.d.ts"]
}
```

`shell-shock.d.ts` is generated by the build and declares the virtual `shell-shock:*` modules (e.g. `shell-shock:console`); type errors on those imports before the first build are expected.

### src/run/command.ts

How a command module works, so you can adapt the sample to what the user asks for:
- `default` export is the handler. **First parameter = parsed options object; remaining parameters = positional arguments, in order.**
- `options` (a `z.object`) and `args` (a `z.tuple`) exports declare the flags and positionals; `.describe()` text becomes help output, `.default()` sets defaults. (Alternatively options can be a plain TS interface with JSDoc — the zod form is clearer for a sample.)
- `metadata` sets title, description, alias and icon for help/banner.
- Nested commands are nested folders: `src/db/migrate/command.ts` → `<cli> db migrate`.

```ts
import { defineMetadata } from "@shell-shock/core";
import { info } from "shell-shock:console";
import * as z from "zod";

export const metadata = defineMetadata({
  title: "Run Script",
  description: "Run a script with the given options.",
  alias: "r",
  icon: "▶"
});

export const options = z.object({
  cwd: z.string().default(".").describe("The working directory to run in."),
  watch: z.boolean().default(false).describe("Re-run when files change."),
  retries: z.number().default(0).describe("How many times to retry on failure.")
});

export const args = z.tuple([z.string().describe("The script to run.")]);

/**
 * Run a script.
 *
 * @param opts - The parsed command options.
 * @param script - The script to run.
 */
function run(opts: z.output<typeof options>, script: z.output<typeof args>[0]) {
  info(
    `Running ${script} in ${opts.cwd} (watch=${opts.watch}, retries=${opts.retries})`
  );
}

export default run;
```

If the user chose `preset-script` without the console plugin, or wants zero framework imports, replace `info(...)` with `console.log(...)` and drop that import.

## 4. Verify

1. `<pm> run build` — expect `dist/bin.mjs` plus one `dist/<command>.mjs` per command.
2. `node dist/bin.mjs run --help` — `run` should list `--cwd`, `--watch`, `--retries` and the `script` argument.
3. `node dist/bin.mjs run hello.js --retries 2` — prints the handler's message.

If the build fails, read the error before changing anything: missing `"type": "module"`, a config file name other than `shell-shock.config.ts`, or no `src/**/command.ts` are the usual causes. Report the actual output to the user rather than claiming success.

## 5. Tell the user

List the files created/modified, the install command that ran, and the three verify commands with their results. Mention that adding a command is just adding `src/<name>/command.ts`.
